## 1. 意图与动机

课程 Final Project 要求：设计一个轻量级 Agent harness，把自然语言 PLC 需求转成能在 CODESYS 中编译的 ST 代码，并与一个现成 Agent 框架在 2×2 设置（2 个框架 × 2 个基座模型）下对比，覆盖 20 道公共题 + 至少 10 道自建题，每题都要有 LTL 规约和测试用例。

评分明确说**不要求自研框架胜过基线**，看重的是实验公平、结果可信、分析有证据、设计逻辑清晰。因此本项目的目标排序是：

1. **评测基础设施可信**：编译、测试、验证三种判定全部自动化，结果可复现；
2. **harness 设计有逻辑、有证据**：每个模块对应作业提出的一个设计问题，并有消融实验佐证；
3. **数据与规约质量高**：自建题来源清楚、覆盖公共题的空白方向，规约和测试的充分性可以量化；
4. 在此基础上尽量拿全进阶项：自动测试、形式化验证、多平台接入、成本效率。

## 2. 目标 / 非目标 / 反目标

**目标**
- G1 自研 harness「STAR」：至少具备生成 + 编译 + 基于编译反馈的修复；完整版还包括自动测试和形式化验证驱动的修复。
- G2 统一评测台：对任何框架生成的 `.st` 文件，用同一套流程给出编译、测试、验证三项判定。
- G3 数据集：20 道公共题 + 12–15 道自建题；每题包含需求、接口、`spec.yaml`（LTL）、测试用例（符合老师的模板）、参考实现。
- G4 实验：2×2 必做组 + 重复运行 + 消融 + 有/无 spec 对照；报告各项指标和成本。
- G5 报告和可运行文档。

**非目标**
- 不做通用编程 agent，只处理单个 POU（FB/FUNCTION/PROGRAM）及其依赖的自定义类型。
- 不做图形化语言（LD/FBD/SFC）。
- 不训练或微调模型。

**反目标（即使能跑也算失败）**
- 评测用的测试用例在生成或修复阶段泄漏给 agent，导致通过率虚高。
- 基线拿到的工具或预算比 STAR 少，对比不公平。
- 规约与测试使用不同的时序约定，导致判定互相矛盾。
- 直接照搬 Agents4PLC 或其他现成 harness 的实现（老师明确禁止）。
- 额度耗尽，正式实验跑不完。

## 3. 约束

- 运行平台：开发机是 Linux；CODESYS（以及 TIA Portal）只能在 Windows 上运行。**【默认】** 用一台 Windows 机器或虚拟机运行 CODESYS 3.5（SP19 或更高），对外提供 HTTP 编译服务。
- 模型：从 DeepSeek / GLM / Qwen / GPT / Claude 家族中选至少两个。**【默认】** 模型 A = DeepSeek 系列，模型 B = Qwen 系列，都通过 OpenAI 兼容接口调用；具体型号和额度以课程实际提供的为准。
- 额度不会补充：正式实验前必须先用 6 道试跑题（每个难度 2 道）估算消耗。
- 独立开发：可以借鉴思路，但代码必须自己写。
- 课程组提供的 PLCModelChecker：https://verify.agents4ics.com/ ，接入方式（网页还是 API）尚未确认。

## 4. 已定的核心设计

### 4.1 统一的扫描周期观测模型（全项目基础约定）

两份官方示例的时序约定不一致：作业文档里输出比输入晚一拍，测试模板里输出同一拍生效。本项目统一采用：

> **第 i 个状态 = 第 i 拍读入的输入 + 第 i 拍 POU 执行完之后的输出和内部变量。**

这与 PLCverif 的默认语义一致，与老师的测试模板一致（同一拍生效），并且能直接映射到"每次调用一次 FB"的测试台。在这个约定下，"停止优先"写成 `G((StopBtn ∨ EStop) → ¬Motor)`；只有确实存在跨拍延迟的需求才使用 `X`。作业示例中带 `X` 的规约在报告里专门分析，说明为什么在本约定下需要改写。

`spec.yaml` 中必须声明 `observation: post-scan`，规约编译器据此生成对应的模型检查断言和运行时监控器。

### 4.2 STAR harness 结构

STAR = **S**pec-anchored（规约锚定）· **T**iered verification（分级验证）· **A**rtifact-centric context（以工件为中心的上下文）· **R**egression-guarded repair（防回退修复）。

原则：**模型负责提出方案，harness 负责执行、记忆和判停。** 调用哪个工具、按什么顺序调用，由 harness 固定决定，LLM 不做工具调度。

流程：

1. **P0 解析（确定性）**：把题目中的 Markdown 接口表解析成 `signature.json`（变量方向、类型、自定义结构体）。
2. **P1 控制契约（LLM）**：输出结构化 JSON，内容包括状态集合与转移、信号优先级表、定时器/计数器表、上电初值表、**假设清单**（需求中的歧义及所作解释）。
3. **P2 代码生成（LLM）**：输入契约 + 签名 + 按特征选出的方言卡片，输出 ST 代码。困难题强制使用 `CASE` 状态机骨架。
4. **T0 独立测试员（LLM，单独上下文）**：只看需求和签名，不看代码，生成扫描周期测试轨迹作为**自测**。
5. **分级验证漏斗**，从便宜到贵依次执行，前一级失败就不往下走：
   - L1 本地语法检查（毫秒级）；
   - L2 CODESYS 编译（秒级）；
   - L3 测试台仿真：自测轨迹 + 规约监控 + 规约引导的随机输入；
   - L4 形式化验证（可选，用于 with-spec 设置）。
6. **诊断压缩器（确定性）**：编译错误去重，定位到出错行前后 ±3 行，匹配方言修复提示；失败轨迹用 delta-debugging 缩短到最短，标出第一个出现差异的周期，并关联到需求条款。
7. **判停与策略（确定性）**：
   - 评分 = 按顺序比较 (编译是否通过, 自测通过数, 规约通过数)；
   - 只接受不降分的修改，始终保留当前最优版本；
   - 代码哈希或诊断哈希重复出现，判定为停滞 → 回到 P1 换一种解法重新生成；
   - 达到轮数、token 或时间预算上限 → 输出最优版本。
8. **自测与需求冲突时**：由一次 Judge 调用依据需求条款判断是代码错还是自测用例错；判定自测错时，丢弃该用例。

上下文管理：**每次 LLM 调用都不带对话历史**，由 harness 从工件（`contract.json`、`code.st`、`diagnostics.json`）现场拼出最小上下文。

### 4.3 方言卡片与错误模式记忆

- 方言卡片：每张不超过 15 行，写明正确用法和常见错误。按签名和需求关键词**确定性触发**（如出现 `VARIANT`、`ARRAY[*]`、`LTIME`、`STRING`、"上升沿"、"延时"），不使用向量检索。
- 错误模式记忆：CODESYS 错误消息模式 → 修复提示。**只从试跑题中积累，正式实验开始前冻结**，并在报告中说明，防止测试集泄漏。

### 4.4 评测台（所有框架共用）

- 编译：调用同一个 CODESYS 编译服务。
- 测试：执行**隐藏的评测测试套件**（即报告中提交的测试用例），这些用例对所有 agent 都不可见。
- 验证：同一份 `spec.yaml` 编译成模型检查断言；记录 通过 / 违反 / 超时 / 不支持。
- **公平性规则**：基线框架可以通过 CLI 或 MCP 使用同一个编译服务，预算上限与 STAR 相同；任何框架都不能接触评测测试套件。

### 4.5 一份规约，多种用途

每道题一个 `spec.yaml`，内容：类型化的 LTL 公式、对应的需求条款编号、观测模型声明。规约编译器从它生成：

- 模型检查器的输入（nuXmv / PLCverif / 课程组的 PLCModelChecker，具体看哪个能接入）；
- Python 有限轨迹 LTL 监控器（测试时同时检查规约）；
- 给 LLM 看的自然语言规约（with-spec 设置）；
- 报告里的逐题规约表。

充分性证据：
- **变异得分**：对参考实现自动生成变异体（交换优先级、删除复位、改比较符、删除初始化、改定时器预设值等），统计测试套件和规约分别能检测出多少；
- **空真性检查**：输出全为 FALSE 的平凡程序至少要违反一条规约；
- **条款追溯矩阵**：需求条款 → 规约编号 → 测试用例编号。

### 4.6 数据集

- 公共题：20 道（easy 6、medium 8、hard 6）。
- 自建题：12–15 道，根据附录 A 的覆盖矩阵定向补齐公共题的空白方向。
- 每题记录：来源类型和链接、改编内容、审核过程、参考实现、领域、语言构造、难度标签。
- 合成题必须通过**往返一致性审核**：参考实现 → LLM 写需求 → 另一个模型只看需求重新实现 → 与参考实现做差分测试；有差异就修改需求，直到一致。
- 难度同时给出主观标注和试跑通过率（经验难度）。

### 4.7 实验

| 项目 | 内容 |
|---|---|
| 必做 | {基线, STAR} × {模型 A, 模型 B}，覆盖全部题目 |
| 基线 **【默认】** | Codex CLI（作业点名）；如果它无法接入所选模型，退而使用 OpenCode，并在报告中说明原因 |
| 重复 | 每组设置 3 次（额度不够时减为 2 次，并在报告中说明） |
| 指标 | 首次编译通过率；修复 n 次后的编译通过率曲线；测试通过率（按任务、按用例）；验证结果（通过/违反/超时）；token；费用；耗时；LLM 调用次数；编译调用次数 |
| 统计 | 均值 ± 标准差，pass@k 与 pass^k；同题配对比较用 McNemar 检验或 bootstrap 置信区间 |
| 消融 | 分别去掉：控制契约、方言卡片、反例最小化、最优保留、独立测试员 |
| 可选 | 有/无 spec 对照（老师建议） |
| 留痕 | 每次运行保存完整轨迹 JSONL，并提供一个简单的轨迹查看器 |

### 4.8 多平台接入

平台适配层统一接口：`compile(source) -> diagnostics`，可选 `run_tests(...)`。

- CODESYS：必做。
- OpenPLC（MATIEC）：**【默认】** 作为速赢项，可同时充当 Linux 本地的快速语法预检。
- TIA Portal（Openness API + SCL 外部源导入 + PLCSIM）：冲刺项，取决于能否拿到 Windows 环境、授权和时间；需要 CODESYS ST 到 SCL 的方言转换。

## 5. 留给实现者决定的事项

- 编程语言和库（建议 Python 3.11 及以上）。
- L1 语法检查的实现方式（自写解析器、tree-sitter 语法，或 MATIEC/RuSTy 前端）。
- 测试台的具体技术路线，在 spike 之后选定：
  - A. 在 CODESYS 里生成 ST 测试台，逐拍调用被测 FB，用 mock 定时器实现虚拟时钟（首选，结果作为权威判定）；
  - B. 自写 Python ST 解释器；
  - C. 开源编译器编译到本地运行。
  B/C 若采用，只作为快速预检，需要和 A 抽样交叉核对。
- 方言卡片的具体内容和触发规则。
- 轨迹查看器的形式。
- 目录结构、配置格式、缓存策略（相同输入不重复调用 LLM）。

## 6. 需要先 spike 的风险

| 风险 | 先验证什么 |
|---|---|
| CODESYS 无界面编译 | 脚本能否打开模板工程、写入 POU、编译并取回错误消息；常驻进程的单次编译耗时 |
| 测试台的虚拟时钟 | 用同名 POU 遮蔽库中 `TON` 等定时器是否可行，或者其他注入时间的办法 |
| PLCModelChecker / PLCverif | 接入方式、支持的 ST 子集、规约格式 |
| 基线接入所选模型 | Codex CLI 能否配置自定义 provider，否则换 OpenCode |
| 额度 | 6 道试跑题的单题 token 消耗，据此决定重复次数和消融规模 |

## 7. 里程碑

M0 环境 spike → M1 数据和规约 → M2 STAR 最小版（契约→代码→编译→修复）→ M3 自动测试和规约监控 → M4 试跑、冻结、正式 2×2 实验 → M5 加分项（形式化验证、消融、有/无 spec、多平台）→ M6 报告。
保底范围：M0–M2 + M4 的 2×2 实验 + 手动测试。
