## 实测与对比的最小执行顺序

### 1. Windows 先跑两个零 token 验收

用组里已有 CODESYS profile 和 template，确认 `configs/runtime.local.json` 指向本机安装。在 Windows 的普通 PowerShell 运行，先确认冒烟测试按顺序得到 `PASS → COMPILE_FAIL → PASS`，再跑两个参考实现。为每次实验使用新目录，保存原始诊断、`simulation_evidence.json`、`trace.json` 和对应任务版本。

~~~powershell
git rev-parse HEAD
uv sync
uv run plc-agent validate-dataset
uv run plc-agent compiler-smoke
$run = "results/raw/nov13-reference-$(Get-Date -Format yyyyMMdd-HHmmss)"
uv run plc-agent test-reference --task-id SELF001 --backend codesys --out-dir "$run/SELF001"
uv run plc-agent test-reference --task-id SELF008 --backend codesys --out-dir "$run/SELF008"
~~~

`SELF001` 有 7 组、39 拍，先验证编译、采样和评分链路。`SELF008` 有 7 组、45 拍，再检查连续扫描计数与动态预置。建议先回收这两项的完整证据，再选择性复跑 `PUB006`。 `PUB006` 的 `BenchElapsed` 已从当前包装器移除，旧 SA33 日志可作为修复前证据。当前精确毫秒用例需要按实际任务周期判断是否能采到。

`PUB018` 的新参考 ST 已有头尾索引和回绕计算，`buffer` 写入及 `item` 出队赋值仍未完成。泛型绑定与目标 CODESYS 的兼容性也需验证，首轮比较先选择能完成采集的任务。 [参考运行入口](https://github.com/Ofeecc/STAR-PLC-Agent/blob/206b54b10d60291a99942dc34fa6dd88c9f0cff1/src/plc_agent/cli.py#L386-L434) · [PUB018 参考 ST](https://github.com/Ofeecc/STAR-PLC-Agent/blob/206b54b10d60291a99942dc34fa6dd88c9f0cff1/codesys/examples/PUB018.json)

### 2. 先做 2 道题的同模型成对比较

推荐 `SELF001`（基本联锁，便于先校准后端）和 `PUB002`（32 位输入历史、最高位与掩码，当前 7 组、39 拍，无物理计时依赖）。每题运行 STAR 和一个 baseline，共 4 次任务级运行。先固定同一个模型、reasoning、编译器、模板、候选评测用例和编译／仿真上限，再对比结果。明确区分生成期间自测与生成完成后的固定用例。

课程说明要求选择**已有 Agent 框架**做 baseline。优先复用组员能提供原始证据的现有框架接入，记录版本、模型和真实工具回调。当前 `configs/experiments.json` 的 E1/E2 是 `custom_tool_loop`。用 `E1/deepseek_harness` 对 `E3` 可以先得到**同模型内部对照**。外部框架若只能使用不同的模型，在报告中列出各自模型，把结果解释为两套系统的比较。 [作业原文](https://github.com/Ofeecc/STAR-PLC-Agent/blob/206b54b10d60291a99942dc34fa6dd88c9f0cff1/requirements/source/Final%20project_ENGLISH.docx) · [当前条件配置](https://github.com/Ofeecc/STAR-PLC-Agent/blob/206b54b10d60291a99942dc34fa6dd88c9f0cff1/configs/experiments.json) · [旧实验协议](https://github.com/Ofeecc/STAR-PLC-Agent/blob/206b54b10d60291a99942dc34fa6dd88c9f0cff1/docs/experiment_protocol.md)

执行人获组内 API 授权后，按选定框架开跑。当前 CLI 的 `run` 读取本地 `results/summary/model_capabilities.json`，该文件未提交到当前基线。缺失时需核对本机已有记录，或由授权人执行 `uv run plc-agent --allow-model-api probe-models --tool-smoke`。探针会遍历配置中的模型，可能产生多次请求。题库哈希已变，若本机有旧 `campaign.json`，先归档旧批次再 `prepare`。

若先做内部对照，以下是第一题的可用命令。两条 `run` 各自消耗模型额度，`test` 读取已生成候选并使用 CODESYS 执行固定用例。先保留第一题的四段输出，再把 `SELF001` 换成 `PUB002` 重复执行。

~~~powershell
uv run plc-agent prepare
uv run plc-agent --allow-model-api run --condition E3 --task-id SELF001
uv run plc-agent test --condition E3 --task-id SELF001
uv run plc-agent --allow-model-api run --condition E1 --driver deepseek_harness --task-id SELF001
uv run plc-agent test --condition E1 --task-id SELF001
~~~

| 题目 | 比较组 | 生成状态 | 首次／最终编译 | 固定用例通过／计划 | 实际采样拍 | 编译／仿真调用 | token／耗时 | 原始目录 |
|---|---|---|---|---|---|---|---|---|
| SELF001 | STAR | 待跑 | — | — | — | — | — | — |
| SELF001 | 已选 baseline | 待跑 | — | — | — | — | — | — |
| PUB002 | STAR | 待跑 | — | — | — | — | — | — |
| PUB002 | 已选 baseline | 待跑 | — | — | — | — | — | — |

四行齐全后报告每题配对结果和原始失败原因。用 `model_calls.jsonl` 的 `request_started` 核对请求次数，用返回的 usage 统计 token，失败响应的已报告用量也计入。模型未报告的用量填缺失。用实测案例描述这两道题的差异，并保留原始配置、候选和 CODESYS 轨迹。旧批次、参考 ST 验收和生成候选各保留独立记录。
