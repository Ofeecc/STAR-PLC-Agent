# 32道题规约逐题审查

审查日期：2026-11-06。对象：`PLC_Agent_本机运行/dataset` 中20道公共题和12道自建题，共207条公式、81组固定测试、576拍预期观察。

本次逐题核对了题目要求、接口、初值、优先级、补充假设、所有公式、原子命题和现有测试。结论是：有一部分题目的分支覆盖较完整；多道状态机题仍缺必须动作、状态保持或数据更新规则，当前不能把“满足已有公式”解释为完整实现题意。

每题一份文件，含问题依据、具体修订建议、已有测试对应和待补场景。这里提供的是静态评审及建议，正式题库、Agent代码和历史实验结果均未修改。建议公式仍需在选定检查器中编码和验收；这份审查不等于形式证明或生成ST的运行结果。

该检查是**六组特定规约的反例复核**，使用的是手工翻译的谓词，未编写通用LTL解析器，也没有运行生成的ST。SELF题的正确输出由项目现有独立Python参考系统给出；它提供辅助一致性依据，不能替代PLC执行证据。

## 整套规约应统一的规则

### 1. 观察时刻

统一一行包含调用开始采样的输入I[k]、调用前保留状态q[k]和调用结束观察的输出O[k]。这时急停当拍关闭写成G(急停→输出关闭)，不能再未经转换地套“下一拍才关闭”。初始条件约束首次调用前的状态；第一调用收到Start仍可以正常启动。

本文建议中`nextPhase`/`postState`指本拍执行完的参考状态，`X(phase)`指下一行的调用前参考状态；二者由完整转移函数绑定。不能把“下一状态”与“下一行输出”混用。

### 2. 每个分支都要写正向动作和保持

互锁与停机属于必要约束，但不足以保证系统完成任务。每个状态至少检查：进入条件、必需输出、离开条件、无事件保持、复位/停止优先级。成功数据操作还必须限定只改哪些字段，以及其他记录保持。

不需要为增加公式数量重复写同一性质；一套初值、完整转移函数与输出方程通常比很多不完整的单向蕴含更可靠。

### 3. 原子命题必须能独立计算

qRun可以绑定上一拍真实观察值。参考phase/history可以由输入历史与需求状态机维护。两种方法都可用，但要说清初值和逐拍递推。待验证程序的内部变量不能不经对应证明就当成需求状态。

`ordered`、`qualified`、`record`、`historyAfter`等名字不是实现。应给确定函数、量词范围、类型和更新顺序；对于有名输出，如PUB002的risingBits，监控器要读真实输出，再与独立计算结果比较，不能把真实输出名直接替换成正确答案。

### 4. 公共题补充解释与原文分开

本次确认20题的requirements与项目保存的原始JSON英文逐字一致；项目保存的题库PDF与用户课件目录中的题库PDF的SHA-256一致：`2c69ce26107e158aea4a9f1bd2efad272b994a9d5207f5e2b20500fdef6e2100`。

边沿还是电平、同拍事件优先级、切模式清状态、变窗重置等，属于后来加入的评测解释。它们可以提高可复现性，但不能声称全部来自原题。两个框架必须收到同一版本解释；PUB010的“超过5秒”与“达到5秒”需尤其明确。

### 5. 时间、数值和有限轨迹

TIME题需要真实调用时间或经验证的受控时钟。dt_ms只是测试的时间约定，不会自动变成FB的虚拟时钟；当前自动仿真适配器也明确排除了带dt_ms的题。500小时维护样例是预期轨迹，不能标成已在短时间完成真实500小时测试。

REAL/LREAL等式需定义与PLC精度相容的比较关系；当前统一绝对1e-5是否适用于全部数值尺度仍需评审。整数/时间溢出要用输入域或显式策略约束。

无限LTL的F/U不能用有限成功测试直接宣称证明。有限监控建议分“已违反”“当前未违反”“尚不能判断”，并对等待超时另立有界任务要求，不能把测试结束就算作无穷活性失败。

### 6. 当前自动化实际检查了什么

`dataset.py`检查字段、接口名和用例结构；它不会判定207条公式是否表达了题意。`functional.py`按固定expected比较真实观察值；它也不执行完整LTL集合。SELF Python参考系统检查预期轨迹和部分安全性质，不是生成ST执行器。

因此，报告应区分“有形式化规约文本”“实现部分轨迹监控”“运行功能测试”“完成模型检查”四种证据。本次六个反例支持规约遗漏的评审结论，不支持生成代码错误率或PLC通过率。

两个框架当前可看到完整任务JSON，包括固定测试。以后若报告泛化能力，应单独准备未暴露的验证用例并标明口径；现有结果只能按原固定测试集解释。

## 修订验收顺序

1. 先按单题建议写出确定初值、总转移和输出方程；公共题不改requirements，将补充解释另列。
2. 为每条关键题意建立“原文要求→规约→至少一个正例/反例”的对应，补齐本次列出的场景。
3. 将ghost状态及数据谓词实现为独立监控器；先用正确参考轨迹和故意错误轨迹验证检查器本身。
4. 选定形式工具后再输出合法目标语法，说明状态/整数/数组编码及活性假设；公式文本不能直接冒充已通过工具验证。
5. 规约更新另存新数据集版本及hash；新结果与旧结果分开保存，两个Agent使用同版后再做比较。

当前CODESYS无界面脚本启动故障是独立的环境问题，本次没有恢复它，也没有用Python代替ST宣称运行成功。
